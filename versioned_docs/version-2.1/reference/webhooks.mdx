You can configure webhooks for 1-Click Health: see [here](/1-click-health/guides/setup#webhooks) in the Setup guide. This allows you to receive 1-Click Health [output](/reference/data/outputs#1-click-health) data asynchronously. (You can alternatively poll the [`GET /1-click/health`](/reference/api/endpoints#get-1-clickhealth) endpoint.)

<table>
  <tr>
    <th>Method</th>
    <td>`POST`</td>
  </tr>
  <tr>
    <th>URL</th>
    <td>Defined by [webhook brand setting](/1-click-health/guides/setup#webhooks)</td>
  </tr>
  <tr>
    <th>Authentication</th>
    <td>Defined by [webhook brand setting](/1-click-health/guides/setup#webhooks) (None, API Key, or Basic Auth)</td>
  </tr>
  <tr>
    <th>Retries</th>
    <td>An immediate attempt, followed by retries after 1 minute, 5 minutes, 30 minutes, 2 hours, 6 hours, and 12 hours (about 22 hours from the first attempt).</td>
  </tr>
  <tr>
    <th>Expected response</th>
    <td>Respond with a `2xx` status (for example `200`) to acknowledge receipt. A non-2xx response or a delivery failure is retried according to the schedule.</td>
  </tr>
  <tr>
    <th>Delivery</th>
    <td>At least once (multiple deliveries possible)</td>
  </tr>
  <tr>
    <th>Retention</th>
    <td>After the final retry, an undelivered event is moved to a dead-letter queue (DLQ), where it is retained for 14 days.</td>
  </tr>
</table>


## Headers

Each webhook request includes the following headers:

<table>
  <tr>
    <th>Header</th>
    <th>Value</th>
    <th>Description</th>
  </tr>
  <tr>
    <td>`Content-Type`</td>
    <td>`application/json`</td>
    <td>The payload is always sent as JSON.</td>
  </tr>
  <tr>
    <td>`User-Agent`</td>
    <td>`VerifiedInc-Webhook/1.0`</td>
    <td>Identifies the request as coming from Verified.</td>
  </tr>
  <tr>
    <td>`X-Webhook-Timestamp`</td>
    <td>Timestamp used to sign the request</td>
    <td>Use this exact value when verifying the webhook signature.</td>
  </tr>
  <tr>
    <td>`X-Webhook-Signature`</td>
    <td>`v1=...`</td>
    <td>HMAC-SHA256 signature of the timestamp and raw request body.</td>
  </tr>
</table>

Any authentication headers you configure in your [webhook brand setting](/1-click-health/guides/setup#webhooks) (API Key or Basic Auth) are also included.

## Verify webhook signatures

Verify each webhook using the signing secret for your webhook:

1. Read the raw request body before parsing JSON, and read `X-Webhook-Timestamp` from the request headers.
2. Compute the expected signature from the secret, timestamp, and raw body, then compare it with the `v1` value in `X-Webhook-Signature` using a constant-time comparison:

   ```text
   v1=HMAC-SHA256(secret, `${timestamp}.${rawBody}`)
   ```

3. Reject requests with a timestamp outside your allowed freshness window to reduce replay risk.

The signing secret is displayed only once when the webhook is created or the secret is rotated. Store it securely when it is shown. For 24 hours after rotation, requests are signed with both the previous and new secrets. During this overlap, accept a valid signature from either secret.


## Payload

```typescript title="GET /1-click/health Response Body"
{
    "event": "1-click.health.lookup",
    "healthDataUuid": string,
    "externalReference"?: string,
    "sentAt": integer,
    ...1ClickHealthEntity
}
```

<table>
  <tr>
    <th>Property</th>
    <th>Type</th>
    <th>Format</th>
    <th>Description</th>
    <th>Example</th>
  </tr>
  <tr>
    <td>`event`</td>
    <td>`string`</td>
    <td>-</td>
    <td>Response from the 1-Click Health lookup</td>
    <td>`"1-click.health.lookup"`</td>
  </tr>
  <tr>
    <td>`healthDataUuid`</td>
    <td>`string`</td>
    <td>[Version 4 UUID](https://en.wikipedia.org/wiki/Universally_unique_identifier#Version_4_(random))</td>
    <td>Unique identifier for the [`1ClickHealthEntity`](/reference/api/types#1clickhealthentity) that will be returned at the end of the 1-Click Health flow</td>
    <td>`"9e12fe5b-5bb8-410a-ac6b-6e053e4c7e8d"`</td>
  </tr>
  <tr>
    <td>`externalReference`</td>
    <td>`string`</td>
    <td>1–256 characters</td>
    <td>Optional customer identifier echoed unchanged from the `POST /1-click/health` request; not a lookup key</td>
    <td>`"appointment-1042"`</td>
  </tr>
  <tr>
    <td>`sentAt`</td>
    <td>`integer`</td>
    <td>[Unix time](https://en.wikipedia.org/wiki/Unix_time) (milliseconds)</td>
    <td>When the payload was sent</td>
    <td>`1760053705000`</td>
  </tr>
  <tr>
    <td>`...`</td>
    <td>[`1ClickHealthEntity`](/reference/api/types#1clickhealthentity)</td>
    <td>See [`1ClickHealthEntity`](/reference/api/types#1clickhealthentity)</td>
    <td>[`1ClickHealthEntity`](/reference/api/types#1clickhealthentity) for the 1-Click Health flow</td>
    <td>See [`1ClickHealthEntity`](/reference/api/types#1clickhealthentity)</td>
  </tr>
</table>

Webhook deliveries are at least once. The same event may be delivered more than once, including during retries, so deduplicate using `healthDataUuid` as the idempotency key. The `externalReference` is for correlating the result with your own record; it cannot be used to retrieve the result.

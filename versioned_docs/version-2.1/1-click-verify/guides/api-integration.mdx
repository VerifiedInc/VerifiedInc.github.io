Implementing the 1-Click Verify API is as simple as getting the user's device IP address and then waterfalling across these three channels. 


## 1. Get user's device IP.

Get the user's device IP address (over a cellular connection if possible), which you'll use in [step 2](#2-get-channel-availability), [step 3](#3-use-autofill-channel), and [step 4b](#b-use-silent-channel). You should do this slightly differently on native mobile vs. web, as described in the sections below.

:::tip Native Mobile vs. Web
**On native mobile (but not on web), you can and should choose a cellular connection even if the user is on WiFi.** Doing this results in much higher success rates, because the autofill and silent channels (which have higher conversion than the SMS channel) only work with device IPs determined over cellular connections.

We provide a [native mobile module](/reference/native-mobile-module) called `VerifiedCellular` that makes this easy to do across Android, iOS, and cross platform frameworks. 
:::


<h3 id="get-device-ip-native-mobile">Native Mobile</h3>

Copy the code for the `VerifiedCellular` [native mobile module](/reference/native-mobile-module) and paste it into your own projects (across iOS, Android, and/or cross-platform frameworks). 

:::info
We don't distribute this as a package so that you don't need to introduce any new dependencies. The code is simple and brief.
:::

Call `VerifiedCellular.getDeviceIp()`. It will return the user's device IP address, determined over a cellular connection:

```typescript title="getDeviceIp() Return Value Example"
"::121:2555:0010"
```


<h3 id="get-device-ip-web">Web</h3>

Call [`GET /1-click/verifications/device-ip`](/reference/api/endpoints#get-1-click-verifications-device-ip) client side, from the user's device. It will return the user's device IP address:

```typescript title="GET /1-click/verifications/device-ip Response Body Example"
{
    "deviceIp": "::121:2555:0010"
}
```

<DeviceIpEndpointAdmonition />

:::warning
**We don't recommend determining the user's device IP any other way.** You may already have the IP or want to use another method to determine it, but there are many subtleties in determining it correctly and normalizing its format so that it works with other Verified endpoints. 

The [`GET /1-click/verifications/device-ip`](/reference/api/endpoints#get-1-click-verifications-device-ip) endpoint handles everything for you, and it's completely free to use, so we strongly recommend using it.
:::

If you aren't able to get the user's device IP, fall back to [step 4c](#c-if-necessary-fall-back-to-sms-channel).


## 2. Get channel availability.

Call [`GET /1-click/verifications/channels?deviceIp={deviceIp}`](/reference/api/endpoints#get-1-click-verifications-channels), server side, with the user's device IP address from [step 1](#1-get-users-device-ip) as the value of the `deviceIp` query parameter.

:::important
**This endpoint requires authentication** (like most Verified API endpoints and all of the other ones referenced in this guide). You should call it from your server, with your Verified API key.
:::

<ApiKeysAdmonition />

The response body will indicate which channels are available:

<Get1ClickVerificationsChannelsResponseBodyExample/>

Your implementation logic should follow the rest of this guide based on which channels are available.


## 3. Use autofill channel.

Call [`POST /1-click/verifications`](/reference/api/endpoints#post-1-click-verifications), setting `channel` to `autofill` and `deviceIp` to the user's device IP address from [step 1](#1-get-users-device-ip):

```typescript title="POST /1-click/verifications Request Body Example (autofill channel)"
{
    "channel": "autofill",
    "deviceIp": "::121:2555:0010"
}
```

<FollowRedirectsSection/>

If the autofill channel succeeds, the response body will contain the user's _verified_ phone number — like magic! You're done.

<Post1ClickVerificationsResponseBodyVerifiedExample/>

:::tip Yes, The Autofilled Phone Number Is Verified!
We use autofill and verify the user's phone number directly from the SIM/eSIM in their device, without any need for user input or an SMS verification code. It's both far easier for the user and far more secure.
:::


## 4. (if necessary) Fall back to silent channel.

If the autofill channel isn't available or fails, fall back to the silent channel. For this channel, the user will have to input their phone number, but they won't have to receive an SMS or use a verification code or link.


### a. Prompt user for phone number.

<SupportedPhoneNumbersAdmonition />

We recommend using a phone number input that auto submits when the user enters 10 digits. (See the [Phone](/1-click-signup/user-experience#phone) screen of the 1-Click Signup User Experience guide for full details.)


### b. Use silent channel.

Call [`POST /1-click/verifications`](/reference/api/endpoints#post-1-click-verifications), setting `channel` to `silent`, `deviceIp` to the user's device IP address from [step 1](#1-get-users-device-ip), and `phone` to the user's phone number from [step 4a](#a-prompt-user-for-phone-number):

```typescript title="POST /1-click/verifications Request Body Example (silent channel)"
{
    "channel": "silent",
    "deviceIp": "::121:2555:0010",
    "phone": "+12125550010"
}
```

<FollowRedirectsSection/>

If the silent channel succeeds, the response body will contain the user's _verified_ phone number — like magic! You're done.

<Post1ClickVerificationsResponseBodyVerifiedExample/>

:::tip Yes, The Phone Number Is Verified, Without an SMS!
We verify the user's phone number directly with the SIM/eSIM in their device, without any need for an SMS verification code or link. It's both far easier for the user and far more secure.
:::


### c. (if necessary) Fall back to SMS channel.

If the silent channel isn't available or fails, fall back to the SMS channel. For this channel, the user will have to input their phone number, receive an SMS, and use a verification code or link.


#### i. Start verification flow.

Call [`POST /1-click/verifications`](/reference/api/endpoints#post-1-click-verifications), setting `channel` to `sms` and `phone` to the user's phone number from [step 4a](#a-prompt-user-for-phone-number):

```typescript title="POST /1-click/verifications Request Body Example (SMS channel)"
{
    "channel": "sms",
    "phone": "+12125550010"
}
```

The response body will contain a `uuid` that you'll use in the next step:

<Post1ClickVerificationsResponseBodyPendingExample/>


#### ii. Deliver verification message.

Call [`POST /1-click/verifications/{uuid}/deliver`](/reference/api/endpoints#post-1-click-verifications-deliver) with the `uuid` from the previous step. This will send a verification SMS to the user's phone number.

You can optionally specify a message format (which defaults to `code` if not included). If the format includes a link — that is, if it's `link`, `codeAndLink`, or `linkAndCode` — you can also specify `redirectUrl` and `redirectUserAfter`, which default to the [redirect URL](/1-click-verify/guides/setup#redirect-url) and [redirect user after](/1-click-verify/guides/setup#redirect-user-after) brand settings.

```typescript title="POST /1-click/verifications/{uuid}/deliver Request Body Example (link)"
{
    format?: "linkAndCode", // defaults to code
    redirectUrl?: "https://hooli.com/verified/1-click-verify", // only relevant if link format is included
    redirectUserAfter?: "phoneVerification" // only relevant if link format is included
}
```

<VerificationSmsFormatsAdmonition/>

The response body will indicate that the message is being sent:

<Post1ClickVerificationsDeliverResponseBodyExample/>


#### iii. Finish verification flow.

How to finish the flow depends on whether a code or link is used.


##### Code


###### A. Prompt user for verification code.

We recommend using a 6 separate single digit inputs that auto submit when the user enters 6 digits. (See the [Verification Code](/1-click-signup/user-experience#verification-code) screen of the 1-Click Signup User Experience guide for full details.)


###### B. Verify verification code.

Call [`POST /1-click/verifications/{uuid}/verify`](/reference/api/endpoints#post-1-click-verifications-verify) with the `uuid` from the earlier API response bodies, including what the user entered in the previous step as `code`:

```typescript title="POST /1-click/verifications/{uuid}/verify Request Body Example"
{
    "code": "111111"
}
```

This will check the user's input against the verification code for this verification flow. The response body will indicate whether or not the check succeeds in the `verified` attribute:

<Post1ClickVerificationsVerifyResponseBodyExample/>


##### Link

If you pass the user to an integrated 1-Click Signup/Health flow on your side, that automatically confirms the user's phone is verified — as long as you include the `uuid` from previous API response bodies as `verificationUuid` in the request body of [`POST /1-click`](/reference/api/endpoints#post-1-click). But if you _don't_ pass the user to such a flow, you need to separately confirm the user's phone is verified. See below for how to do this (and why it's necessary).

{/* <SequenceDiagramTextToSignupConfirmUsersPhoneIsVerified/> */}


###### A. Parse URL parameter.

When a user completes verifying with a verification link, we redirect them to the redirect URL you define via the [redirect URL](/1-click-verify/guides/setup#redirect-url) brand setting (or [`redirectUrl`](/reference/api/endpoints#post-1-click-verifications-deliver) API input). 

We append a URL parameter that depends on what you set for the [redirect user after](/1-click-verify/guides/setup#redirect-user-after) brand setting (or [`redirectUserAfter`](/reference/api/endpoints#post-1-click-verifications-deliver) API input). When it's set to **"1-Click Verify"** (`"phoneVerification"`), we redirect the user after we verify their phone number and append a `verificationUuid` parameter, which lets you check that the user's phone was verified:

```
{redirectUrl}?verificationUuid={verificationUuid}

https://hooli.com/verified/1-click-verify?verificationUuid=68b7bf30-1a2d-4fcc-a2c8-be7de29e5b19
```

**Parse the value of this `verificationUuid` parameter,** which you'll use in the next step.

<Admonition type="note" title="Sandbox Environment">
In the [Sandbox](/reference/api/environments#sandbox) environment, we also append an `env=sandbox` parameter (for example `...?verificationUuid={verificationUuid}&env=sandbox`). This lets you tell test requests apart from live ones when you use the same redirect URL in both environments.
</Admonition>

<Admonition type="danger">
**A user arriving at your [redirect URL](#redirect-url) with a `verificationUuid` URL parameter is NOT a technical guarantee that the user's phone is verified!** If your use case needs such a guarantee, you must confirm the phone is verified using [step 4ciiiB](#b-get-verification-status) and [step 4ciiiC](#c-check-verified).
<details>
    <summary>Why is this the case?</summary>

    A bad actor can figure out what the redirect URL is (for example by simply going through the flow themselves) and then append a `verificationUuid` parameter with a random UUID value.

    So, to confirm the user's phone is verified, you need to _use_ the value of the `verificationUuid` parameter to call `GET /1-click/verifications/{uuid}` (see [step 4ciiiB](#b-get-verification-status)) and then check `verified` in the response (see [step 4ciiiC](#c-check-verified)). This _can't_ be spoofed, because a bad actor doesn't have any way of correctly guessing a _valid_ UUID value for `verificationUuid`.
</details>
</Admonition>


###### B. Get verification status.

Pass the `verificationUuid`, which you parsed in the previous step, to your server. The server should use your Verified API key to call [`GET /1-click/verifications/{uuid}`](/reference/api/endpoints#get-1-click-verifications):

```
GET /1-click/verifications/{uuid}
```

<Admonition type="note">
The endpoint you should use here is **`GET /1-click/verifications`**, which is different than `GET /1-click`.
</Admonition>

The response body will be a [`1ClickVerificationEntity`](/reference/api/types#1clickverificationentity):

```typescript title="GET /1-click/verifications Response Body"
{
    ...1ClickVerificationEntity
}
```
<OneClickVerificationEntityExampleSmsLink/>


###### C. Check `verified`.

Check that `verified` is `true` (or, equivalently, that `status` is `"verified"`), which means the user's phone is verified. Otherwise, it may be spoofed.

## Handle Errors

To ensure your integration is robust, handle all of the 1-Click Verify [errors](/reference/api/errors#1-click-verify). 

Many errors can be handled simply by starting a new 1-Click Verify flow. If an error indicates that a particular channel failed, and there are one or more other channels still available, you should fall back to the other channel(s), as indicated in the guide above.

## Satisfy Compliance Requirements

Autofilling phone numbers, verifying phone numbers, and sending SMS are subject to strict regulations and carrier review in the US. You must satisfy the following compliance requirements for us to approve your integration for [Production](/reference/api/environments#production) access.


### Autofill and Silent Channels

Before you call `POST /1-click/verifications` ([step 3](#3-use-autofill-channel) and [step 4b](#b-use-silent-channel)), you must have the user agree to your terms, and those terms must include this 1-Click Verify autofill channel consent language:

> You authorize your wireless carrier to use or disclose information about your account and your wireless device, if available, to `{Brand Name}` or its service providers for the duration of your business relationship, solely to help us identify you or your wireless device and to prevent fraud. See our Privacy Policy to see how we treat your data.

- **Replace `{Brand Name}` with your brand name.**

:::warning You Must Use Exactly This Language
This language has been approved by all three major carriers in the US: Verizon, T-Mobile, and AT&T. It's simply not feasible to get approval from all of them for changes to the language. Therefore, **we cannot approve your integration unless you use _exactly_ the language above.**
:::

For example, as our User Experience guide describes [here](/1-click-verify/user-experience#opt-in), you can use a button with language that indicates that the user agrees to your terms by continuing:

### SMS Channel

Before you call `POST /1-click/verifications/{uuid}/deliver` ([step 4cii](#ii-deliver-verification-message)), you must include this 1-Click Verify SMS channel consent language:

> I authorize [Verified](https://verified.inc) to send me SMS verification texts at the number provided. Msg & Data rates may apply.

- **Link "Verified" to https://verified.inc and make it underlined and a different color than the rest of the text** (so the user knows it's a link).
- **Make this visible to the user, somewhere on the page, before you call `POST /1-click/verifications/{uuid}/deliver`.**

_See our [Demo](https://1-click.demo.verified.inc) for an example of this._

## Go Live!

**When you're ready to go live, you made need to request approval for [Production](/reference/api/environments#production) access,** depending on how you're using other Verified products:

1. Go to the **Brand Details** page for your brand in the Verified [Dashboard](https://dashboard.verified.inc).
2. Click the **Production** tab in the upper right, and make sure your brand settings are configured as you intend them to be.
3. Click the **Request Approval** button under the API Keys section.
4. Complete the **steps** listed in the dialog.
5. Click the **Submit Request** button.


### Swap Sandbox for Production

**Once you have Production access, just swap Sandbox for Production:**

1. Swap your Sandbox API key for your Production API key.
2. Swap the [Sandbox base URL](/reference/api/environments#sandbox) for the [Production base URL](/reference/api/environments#production).

**Then you'll be live with 1-Click Verify! ✅**
